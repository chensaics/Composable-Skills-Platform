使用 CSP 审查能力对产品设计进行多维度批判性审查——不罗列测试方向，而是从更高层次判断产品定位、设计逻辑和整体方向是否合理。

> 测试回答"代码做对了吗"，审查回答"做的东西对吗"。

## 审查 vs 测试

| 维度 | 测试（`000-test_pipeline_csp.md`） | 审查（本文件） |
|------|----------------------------------|-------------|
| 核心问题 | 功能是否符合 Spec | 产品设计本身是否有问题 |
| 视角 | 质量工程师——找缺陷 | 产品总监+UX+业务+技术——找方向问题 |
| 方法 | 等价类/边界值/状态迁移/场景法 | 批判性思维/跨维度交叉验证/二阶效应推演 |
| 产物 | pass/fail + 测试证据 | finding + 影响分析 + 优化建议 + 优先级 |

## 审查流程

### Phase R0：审查启动与上下文装载

按 `[[workflow:csp-knowledge-hub]]` 四层入口定位当前状态：

1. 读 `docs/strategy/STRATEGY.md` —— 产品定位锚点
2. 读 `docs/strategy/ROADMAP.md` —— 版本序列与功能清单
3. 读活跃 PRD SPEC（`docs/prd/PRD-{slug}.md`） —— 待审查的功能设计
4. 读 Spec（`.csp/planning/spec.md`）+ 技术方案（`.csp/tech-design/`）
5. 读既有 findings（`.csp/audit/`、`.csp/critic/`、`.csp/review/`）—— 避免重复审查
6. 读 `docs/analysis/CURRENT-STATE-{date}.md` —— 当前产品数据

**检查点**：审查上下文就绪卡——战略锚点/版本范围/以往 finding 数/当前数据基线。

### Phase R1：产品定位与战略审查（站在产品总监视角）

**审查什么**：不是功能细节，是"做这个版本对吗"。

#### R1.1 定位一致性

| 审视点 | 问什么 | 不通过 → |
|--------|--------|----------|
| 战略锚点对齐 | 本版本功能是否服务于 STRATEGY 定义的诊断/方针/投资主线？ | 功能偏离战略——建议砍或降级 |
| 价值主张清晰度 | 这个版本交付后，用户/市场一句话能说清产品是做什么的吗？ | 功能堆砌无主线——建议收敛 |
| 非核心扩张 | 本版本是否有功能超出了核心业务场景？是故意拓展还是 scope creep？ | 无意识扩张——标记风险，建议审视 Phase 2.5 |
| 竞品差异化 | 本版本所做的，和竞品的差异是可以感知的还是自说自话的？ | 伪差异化——建议强化差异表达或放弃方向 |

#### R1.2 不做之事的审视

对照 STRATEGY 明确 list 了"不做什么"——本版本是否有不该做的混进来了？

**裁决**：每项偏离标记 finding + 影响分析 + 建议（纳入/降级/剔除/需澄清战略）。

---

### Phase R2：用户与体验审查（站在 UX Director 视角）

**审查什么**：不是"按钮对不对"，而是"用户能不能完成他想做的事，过程中有没有被伤害"。

#### R2.1 用户需求穿透

| 审视点 | 问什么 | 典型反模式 |
|--------|--------|-----------|
| 场景真实性 | 本版本解决的场景，是用户真的在遇到的，还是"我觉得用户应该需要"？ | 解决方案找问题——功能很强但没人在用 |
| Jobs-to-be-Done | 用户雇佣这个产品/功能来完成什么工作？功能设计是否让它更好完成？ | 只关注功能参数，不关注用户任务完成度 |
| 核心路径优先级 | 最高频的用户路径是否被优先保证？边缘场景是否挤占了核心体验的资源？ | 为了覆盖"万一"而牺牲"每天"的性能/可用性 |
| 用户分层 | 不同用户角色的需求是否有冲突？哪些是被牺牲的？ | 管理员功能侵占普通用户体验 |

#### R2.2 交互设计审查

按 Nielsen 10 可用性启发式对照——每条 finding = 具体交互问题 + 影响分析 + 严重度：

| 启发式 | 审查视角 |
|--------|---------|
| ① 系统状态可见性 | 用户操作后是否立刻有反馈？长时间操作是否有进度？当前在哪一步？ |
| ② 系统与现实匹配 | 使用的语言/概念是否用户能理解？还是技术黑话/内部术语？ |
| ③ 用户控制与自由 | 误操作能否撤销？是否支持"返回"？退出是否明显？ |
| ④ 一致性与标准 | 同一操作在不同模块的入口/反馈/交互是否一致？是否遵循平台惯例？ |
| ⑤ 错误预防 | 高危操作是否有二次确认？约束条件是否前置（如格式校验在输入时而非提交后）？ |
| ⑥ 识别而非回忆 | 选项/操作是否可见？用户是否需要记住上一步的信息才能继续？ |
| ⑦ 灵活性与效率 | 高频用户是否有快捷路径？是否有键盘快捷键/批量操作？ |
| ⑧ 美学与极简 | 信息密度是否合适？页面是否被不必要的信息/操作淹没？ |
| ⑨ 帮助与错误恢复 | 错误信息是否告诉用户"出了什么问题 + 怎么解决"？还是裸报错栈？ |
| ⑩ 帮助与文档 | 复杂流程是否有内联提示？不需查文档就能完成？ |

#### R2.3 状态覆盖完整性

审查每个交互路径的状态覆盖：

| 状态 | 是否设计 | 典型遗漏 |
|------|---------|---------|
| Loading | 数据加载中用户看到什么？ | 白屏/无反馈——用户不知道在加载还是坏了 |
| Empty | 无数据时的首次体验 | 空白页——用户不知道是没数据还是 bug |
| Error | 出错后的用户路径 | 裸错误栈/无重试入口/无用户可操作的信息 |
| Success | 操作成功后的反馈 | 成功无声——用户不确定操作生效 |
| Disabled | 不可操作的状态 | 灰掉无解释——用户不知道为什么不能点 |
| Edge case | 极端情况下 | 超大数据/无网络/旧版本数据兼容 |

### Phase R3：业务价值与商业审查（站在业务总监视角）

**审查什么**：不是"功能能不能做"，而是"值不值得做"。

#### R3.1 业务价值评估

| 审视点 | 问什么 | 信号 |
|--------|--------|------|
| 价值假设 | 做这个功能的假设是什么？"如果做 X，预期 Y 指标变化 Z%"——假设是否可验证？ | 无法验证的假设 = 信仰，不是业务决策 |
| 度量锚点 | 这个功能做完了，怎么知道成功了？北极星子指标预期变化？ | 无度量锚点 = 做了也不知道效果 |
| 成本-价值比 | 实现成本 vs 预期业务价值。价值能 cover 成本吗？ | 高成本低价值 = 优先级错位 |
| 机会成本 | 做了这个，不做什么？被推迟的功能是否有更高的业务价值？ | 未评估机会成本 = 隐性亏损 |
| 竞品时间窗 | 这个方向有先发优势窗口吗？推迟一个版本会失去什么？ | 时间敏感的机会 → 提前优先级 |

#### R3.2 商业模型审视

- **变现路径**：这个版本对变现的贡献是什么？直接（新付费功能）/ 间接（提升留存→降低流失）/ 无？
- **成本结构**：新增功能是否有持续的运营成本（云资源/第三方服务/人工）？是否在可接受范围内？
- **单位经济**：如果这个功能服务更多用户，边际成本是上升/持平/下降？
- **增长杠杆**：这个功能放在增长飞轮的哪个位置？获客/激活/留存/变现/传播？

---

### Phase R4：技术可行性审查（站在架构师视角）

**审查什么**：不是"代码能不能写出来"，而是"在现有架构和约束下，这个设计合理吗"。

| 审视点 | 问什么 | 不通过 → |
|--------|--------|----------|
| 架构匹配度 | PRD 描述的功能，现有架构是否支撑？是否需要大规模重构？ | 架构不匹配——评估重构代价，考虑分阶段 |
| 技术债影响 | 这个功能的实现会被现有技术债阻碍吗？做完了会不会引入新债？ | 被债阻碍——先清偿再建设 |
| 关键依赖就绪度 | 依赖的外部服务/组件/库是否成熟可用？许可证是否兼容？ | 依赖未就绪——标记阻塞，安排就绪时间线 |
| 性能约束 | 功能在预期规模下是否有性能风险？有没有去重/缓存/异步方案？ | 无性能预案——补充性能设计 |
| 可观测性 | 新功能的关键路径是否有日志/指标/告警计划？ | 裸奔上线——补充可观测设计 |
| 回滚策略 | 上线后出问题能否快速回滚？数据迁移是否可逆？ | 不可回滚——标记高风险，必须有应急预案 |

---

### Phase R5：风险审查（站在风控视角）

**审查什么**：不是"有没有 bug"，而是"上线后最坏会怎样，概率多大，值不值得冒这个险"。

#### R5.1 风险矩阵

| 风险类型 | 审查点 | 严重度判定 |
|---------|--------|-----------|
| 数据风险 | 功能是否涉及用户数据的新增/修改/删除？数据丢失/泄露最坏影响？ | 涉及 PII → 必须数据保护审查 |
| 安全风险 | 新入口/新接口的鉴权和越权是否设计完备？ | 新端点无鉴权设计 → CRITICAL |
| 合规风险 | 是否涉及 GDPR/个人信息保护/行业监管？ | 标记合规缺口 |
| 兼容风险 | 新功能是否 break 旧版本/旧数据/旧 API？ | breaking change → 必须有迁移方案 |
| 依赖风险 | 依赖的外部服务 SLA？挂了怎么办？ | 单点依赖无降级 → HIGH |
| 运营风险 | 上线是否需要特殊操作？是否需要人工介入？ | 手工操作多 → 建议自动化，至少写 runbook |
| 并发风险 | 多人/多系统同时操作是否有冲突？ | 无并发控制 → 可能产生脏数据 |

#### R5.2 被忽略的场景

**批判性思维核心问题**——站在最强反对者视角穷举"这个设计在什么情况下会出问题"：

- 用户不按设计者意图使用时？（用户不是机器人——他们会绕路、跳过、误解）
- 极端数据下？（1 条 → 100 万条 → 1 亿条，系统行为是否一致？）
- 网络/服务不可用时？（依赖挂了是降级还是崩溃？）
- 多个功能同时操作时？（A 用户在编辑、B 用户在删除——冲突怎么处理？）
- 时间穿越时？（跨时区/夏令时/闰秒/旧数据迁移到新 schema）

#### R5.3 关键假设挑战

每个假设反问"如果这个假设是错的，设计还成立吗"：

| 假设 | 反证 | 如果反证成立 |
|------|------|------------|
| "用户会按引导一步一步操作" | 用户可能跳过/乱点/直接 URL 进入 | 跳过引导的状态是否处理？ |
| "数据量不会超过 X" | 上线 3 个月后数据量超过 10X | 性能是否会恶化？是否需要分页/归档？ |
| "这个第三方服务会一直在" | 服务商关闭/涨价/改 API | 是否有替代方案？迁移成本多大？ |
| "管理员会正确配置" | 管理员配错/不配/配了矛盾的参数 | 系统行为是报错还是静默异常？ |

### Phase R6：数据与指标审查

**审查什么**：不是数据好不好看，而是数据告诉我们产品方向对不对。

调用 `[[skill:csp-product-metrics-review]]` 获取北极星指标健康度 + `[[skill:csp-user-analytics]]` 获取用户行为数据：

| 审视点 | 问什么 | 发现类型 |
|--------|--------|---------|
| 指标趋势 | 核心指标在上一个版本是上升/持平/下降？趋势能否支撑本版本的假设？ | 趋势恶化而本版本未包含修正 → 方向问题 |
| 功能采用 | 哪些功能用户在用？哪些不碰？本版本新增的功能和已有采用率数据是否一致？ | 在低采用率模块上堆功能 → 资源错配 |
| 用户流失点 | 用户在哪个环节流失最严重？本版本是否针对了最大漏点？ | 忽略最大漏点做新功能 → 优先级问题 |
| A/B 结论 | 上一个版本的实验结论是否被本版本的设计采纳/否定/忽略？ | 忽略实验结论 → 数据驱动失效 |

---

### Phase R7：长期发展审查

**审查什么**：不是这个版本能不能发，而是这个版本在 3 个版本后的回顾中是否还合理。

| 审视点 | 问什么 |
|--------|--------|
| 架构演进一致性 | 这个设计是让架构往正确的方向演进，还是在架构上打补丁？ |
| 平台化可复用性 | 这个功能做完能否沉淀为平台能力？还是纯业务一次性代码？ |
| 复杂性天花板 | 当前设计在功能量 ×3、用户量 ×10 时还成立吗？哪里会先崩？ |
| 团队可维护性 | 半年后的新成员能否从 PRD+Spec 理解这个功能为什么这么做？ |
| 版本间一致性 | 这个版本的功能和上/下版本是否逻辑自洽？版本间是不是在反复横跳？ |

## 审查与测试的分工

```
000-product-review_csp.md（本文件）        000-test_pipeline_csp.md
─────────────────────────────            ─────────────────────────
审查"做的东西对吗"                         测试"做对了吗"
                                              │
R1 产品定位（PRD vs 战略）                   │
R2 用户与体验（Nielsen 10/状态覆盖）         │
R3 业务价值（ROI/机会成本）                  │
R4 技术可行性（架构/依赖/性能）              │
R5 风险（最坏情况/被忽略场景/关键假设）       │
R6 数据指标（趋势/采用率/流失点）            │
R7 长期发展（架构演进/平台化/可维护性）       │
                                              │
审查 findings ──→ 流向 product-planning       │
（方向问题 → Phase 2.5 审视候选）             │
                                              │
                                      测试 findings ──→ 流向 develop pipeline
                                      （功能缺陷 → 05 修复）
```

- **审查找方向问题** → 回流到产品规划的 Phase 2.5（集成审视）和 Phase A（现状评估）
- **测试找功能缺陷** → 回流到开发 Pipeline 的 05（修复）
- **两者互补不重叠**：审查不以 pass/fail 判功能对错，测试不判断产品方向

## 自决策授权

审查维度选择、严重度判定、优先级排序、建议方向——自行裁决，记入审查报告。打断条件仅 2 类：发现战略根本矛盾（STRATEGY 本身需要修改）/ 发现 P0 安全/合规风险（需立即阻断发布）。

**审查不等于否定**：审查发现的问题不是"你做错了"的指责——是"这个设计在某种视角下可能存在问题，请你考虑"的信号。审查报告的最终裁决权在产品和开发团队，审查只提供多维度分析。

**批判性思维铁律**：
1. 先假设你认为正确的结论是错误的——站在对立面找反证
2. 推演二阶效应——这个改动 3 个版本后会导致什么
3. 跨维度交叉——用户体验的问题可能是商业模型问题导致的
4. 不自证——不是列一堆证据证明设计是好的，而是主动找设计中可能出问题的地方

每个阶段按进度条播报，全部完成后输出审查总报告。
